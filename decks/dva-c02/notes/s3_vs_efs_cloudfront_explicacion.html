¿Por qué S3 y no EFS para servir un sitio estático global?

La pregunta: sirves un sitio estático (imágenes, videos, HTML, JS) con la menor latencia posible para usuarios globales. ¿Qué combinación usas?

Respuesta: C — Amazon S3 (almacenamiento) + CloudFront (CDN).

Tu duda: "yo recuerdo que EFS es más rápido"Tienes razón en un matiz: para una instancia EC2 que lee archivos por NFS dentro de la misma región, EFS da baja latencia de sistema de archivos. Pero esa NO es la comparación de esta pregunta. Aquí el criterio es "servir estáticos a usuarios globales por HTTP con la menor latencia", y ahí lo que manda es estar cerca del usuario (CDN en el edge), no qué disco es más rápido en el datacenter. La velocidad de EFS es irrelevante si tus bytes tienen que cruzar el océano en cada request.

1. La clave: la latencia global la resuelve la DISTANCIA, no el disco

Para un usuario en Tokio pidiendo una imagen alojada en us-east-1 (Virginia), la mayor parte de la latencia es la distancia física (ida y vuelta de los paquetes por la red). No importa si el archivo está en un disco EFS que responde en microsegundos: el viaje transoceánico domina.

flowchart LR subgraph SIN["Sin CDN: siempre vas al origen regional"] direction LR T1["Usuario Tokio"] -->|"~150-200 ms transoceanico"| O1[("Origen en us-east-1")] end subgraph CON["Con CloudFront: cache cerca del usuario"] direction LR T2["Usuario Tokio"] -->|"~pocos ms"| E2["Edge de CloudFront en Tokio"] E2 -.->|"solo la 1a vez (cache miss)"| O2[("Origen S3")] end

CloudFront cachea el estatico en una edge location cercana. La velocidad interna del origen casi no cuenta.

Idea central (latencia)Para estáticos globales, "rápido" = cerca del usuario. Eso lo da la CDN (CloudFront) con el cache en el edge. Hay dos momentos:
  • Cache hit (la mayoría de las peticiones): CloudFront sirve desde el edge y no toca el origen. La latencia es la misma sin importar si el origen sería S3 o EFS.
  • Cache miss (solo la 1a vez de cada zona): CloudFront va al origen. Aquí sí hay diferencia de latencia, y es donde S3 gana (ver sección 2).

2. S3 y EFS son cosas distintas (no compiten aquí)

AspectoAmazon S3Amazon EFS
TipoAlmacén de objetosSistema de archivos (NFS)
Cómo se accedeAPI HTTP(S) directamente (GET por URL)Se monta por NFS en una instancia (EC2/ECS/EKS/Lambda) dentro de una VPC
AlcanceObjeto direccionable globalmente por URLRegional (o One Zone); vive dentro de una VPC
¿Origen directo de CloudFront?Sí (integración nativa, OAC)No directamente; necesitarías EC2/servidor delante para exponerlo por HTTP
Caso de uso típicoSitios estáticos, media, backups, data lakeArchivos compartidos entre varias instancias (POSIX, file locking)
Modelo de costoPor GB almacenado + requests, muy barato para estáticosPor GB de sistema de archivos; pensado para cómputo que monta el FS
Quién tiene MENOS latencia en el cache missS3. En el cache miss (único momento donde el origen importa):
  • S3 → CloudFront: S3 es un origen HTTP nativo. CloudFront lo alcanza directo por el backbone de AWS. Es 1 salto: edge → S3.
  • EFS → CloudFront: EFS no habla HTTP, es NFS. CloudFront no puede usarlo como origen. Obliga a meter un EC2 en medio que monte el EFS por NFS y responda HTTP. El miss se vuelve: edge → EC2 → NFS → EFS → EC2 procesa → responde. Más saltos = más latencia.
Por eso S3 gana: empata con EFS en los cache hits (origen irrelevante) y gana en los cache miss (salto directo por backbone vs EC2 intermedio).
Tu recuerdo "EFS es más rápido"Es cierto, pero para otro escenario: una EC2 leyendo archivos por NFS dentro de la misma región. Eso no aplica aquí, porque al servir estáticos por CDN el origen casi no se toca (solo en el miss), y en ese miss EFS ni siquiera es un origen válido: necesita el EC2 intermedio que le añade latencia.

3. La arquitectura correcta (S3 + CloudFront)

flowchart LR U["Usuarios globales"] --> CF["CloudFront (edge locations)"] CF -->|cache hit| U CF -.->|"cache miss: OAC"| S3[("Bucket S3 privado
HTML, JS, imagenes, video")] S3 -.-> CF
  1. Subes los estáticos a un bucket S3.
  2. Creas una distribución CloudFront con ese bucket como origen.
  3. Usas Origin Access Control (OAC) para que el bucket quede privado y solo CloudFront pueda leerlo.
  4. CloudFront cachea en el edge cercano a cada usuario. La primera petición de una zona va al origen (cache miss); las siguientes se sirven desde el edge (cache hit).
Bonus de examenCon OAC, S3 queda cerrado al público y nadie puede saltarse la CDN yendo directo a la URL del bucket. Es la forma recomendada actual (antes era OAI).

4. Por qué NO las otras opciones

OpciónVeredictoMotivo
A. EFS + CloudFrontNoEFS es NFS, no habla HTTP, así que no es origen válido de CloudFront. Necesitaría un EC2 intermedio que lo sirva por HTTP, y en el cache miss ese salto extra añade latencia frente a S3, que CloudFront alcanza directo por backbone.
B. S3 Glacier + CloudFrontNoGlacier es archivado con recuperación de minutos a horas. Sirve para retener, no para servir con baja latencia.
D. EC2 + CloudFrontNo óptimoEC2 es cómputo regional; para estáticos es innecesario administrar servidores. Se usa cuando el contenido es dinámico.
C. S3 + CloudFrontCorrectaAlmacén de objetos durable y barato, con integración nativa como origen de la CDN. Escala sin servidores.

5. Cuándo SÍ usarías EFS (para no confundirte)

EFS brilla en otro escenarioEFS es la respuesta cuando necesitas un sistema de archivos compartido montado por varias instancias a la vez (EC2/ECS/EKS/Lambda), con semántica POSIX y file locking: directorios home compartidos, un CMS donde varios servidores escriben los mismos archivos, cargas que necesitan lecturas/escrituras concurrentes de archivos. Ahí S3 (que es objetos, no un FS montable) no encaja.
Necesito...Servicio
Servir estáticos por web / globalesS3 (+ CloudFront)

Disco de bloque para UNA instancia (como un SSD)EBS
Archivado barato de largo plazoS3 Glacier

6. Resumen para el examen (DVA-C02)

Puntos clave
  • "Estático + baja latencia global" → S3 + CloudFront casi siempre.
  • La latencia global la resuelve la CDN en el edge (cercanía al usuario), no la velocidad del disco de origen.
  • S3 = objetos por HTTP, origen nativo de CloudFront (con OAC). EFS = file system NFS regional, se monta en cómputo, no habla HTTP ni se conecta directo a CloudFront.
  • "EFS es más rápido" solo aplica a lectura de archivos desde una instancia en la misma región; irrelevante para servir estáticos globales.
  • Glacier = archivar (lento). EC2 = cómputo/dinámico. EBS = bloque para una instancia.
