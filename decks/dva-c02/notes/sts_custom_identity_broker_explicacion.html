STS en un custom identity broker: cómo se obtienen credenciales temporales

La pregunta: en un custom identity broker, ¿qué llamadas de STS se usan para obtener credenciales temporales y qué devuelven?

Respuesta: C — AssumeRole o GetFederationToken; devuelven access key ID + secret access key + session token temporales (con expiración).

1. ¿Qué es un custom identity broker y qué problema resuelve?

Imagina una empresa con miles de empleados que ya se autentican contra su directorio corporativo (LDAP / Active Directory). Quieres que esos usuarios accedan a recursos de AWS sin crearles un usuario IAM a cada uno (no escala y son credenciales permanentes que hay que rotar).

La solución es federación: un identity broker (una app que tú escribes) autentica al usuario contra tu directorio y luego pide a AWS credenciales temporales en su nombre. Esas credenciales caducan solas, así que no hay claves de larga duración regadas por ahí.

Idea centralEl broker traduce una identidad de tu directorio (que AWS no entiende) en credenciales AWS temporales (que AWS sí entiende). La pieza de AWS que emite esas credenciales es STS (Security Token Service).

2. El flujo paso a paso

sequenceDiagram participant U as Usuario (empleado) participant B as Identity Broker (tu app) participant DIR as LDAP / Active Directory participant STS as AWS STS participant AWS as Recurso AWS (p.ej. S3) U->>B: 1. Inicia sesion B->>DIR: 2. Verifica usuario/clave DIR-->>B: 3. Autenticado OK B->>STS: 4. AssumeRole o GetFederationToken STS-->>B: 5. Credenciales TEMPORALES
(AccessKeyId + SecretAccessKey + SessionToken + Expiration) B-->>U: 6. Entrega las credenciales temporales U->>AWS: 7. Llama a AWS con esas credenciales Note over U,AWS: Al expirar, se piden unas nuevas (paso 4)
Requisito claveEl broker necesita credenciales AWS activas propias (de un usuario/rol IAM con permiso para llamar a STS) para poder pedir las credenciales temporales. El usuario final nunca tiene credenciales IAM propias.

3. ¿Qué devuelven AssumeRole / GetFederationToken?

Ambas crean una sesión y devuelven un juego de credenciales temporales. Los tres valores que siempre vienen:

ValorQué es
AccessKeyIdIdentificador de la clave (como el "usuario" de la credencial).
SecretAccessKeyLa clave secreta para firmar las peticiones.
SessionTokenToken de sesión que debe acompañar a las otras dos (es lo que marca la credencial como temporal).
ExpirationFecha/hora en que caducan. Después de eso, hay que pedir unas nuevas.
La señal de "credencial temporal"Si ves tres partes (AccessKeyId + SecretAccessKey + SessionToken), es temporal, de STS. Una credencial IAM permanente solo tiene dos (AccessKeyId + SecretAccessKey), sin session token.

AssumeRole vs GetFederationToken (ambas válidas aquí)

AspectoAssumeRoleGetFederationToken
IdeaAsumir un rol IAM y obtener sus permisos temporalmenteFederar a un usuario y darle credenciales temporales acotadas por policy
Quién la llamaUn rol o usuario IAMUn usuario IAM (típicamente el del broker)
Permisos resultantesLos del rol asumido (intersección con session policy)Intersección de los permisos del usuario que llama y la policy que pasas
Duración15 min a 12 h (según el máximo del rol)15 min a 36 h (por defecto 12 h)

4. Por qué NO las otras opciones

OpciónVeredictoMotivo
A. GetCallerIdentity; credenciales permanentesNoGetCallerIdentity solo te dice quién eres (la identidad de quien hace la llamada). No emite credenciales de ningún tipo. Además aquí se buscan temporales, no permanentes.
B. AssumeRoleWithSAML únicamente; requiere store SAMLNoAssumeRoleWithSAML existe, pero exige un IdP SAML. El escenario del broker autentica contra LDAP/AD directamente (no SAML), así que no aplica. Y decir "únicamente" es falso: hay más de una opción.
D. CreateUser + CreateAccessKey; claves de larga duraciónNoEso crea un usuario IAM y credenciales permanentes: justo lo que la federación quiere evitar. No escala (miles de usuarios) y las claves permanentes son un riesgo de seguridad.
C. AssumeRole o GetFederationToken; access/secret/session temporalesCorrectaSon las APIs de STS pensadas para el custom identity broker; devuelven credenciales temporales con expiración.

5. Mapa de decisión de las APIs STS (para no confundirlas)

EscenarioAPI de STS
Custom identity broker (LDAP/AD, tu propia app)AssumeRole o GetFederationToken
El IdP corporativo habla SAML 2.0AssumeRoleWithSAML
Login con proveedor web / OIDC (Google, Facebook, Cognito, OIDC)AssumeRoleWithWebIdentity
Acceso cross-account o elevar privilegios (MFA)AssumeRole
Solo saber quién soy (debug de identidad)GetCallerIdentity (no da credenciales)

6. Resumen para el examen (DVA-C02)

Puntos clave
  • Credenciales temporales → siempre STS.
  • Custom identity broker (LDAP/AD) → AssumeRole o GetFederationToken.
  • Devuelven 3 piezas + expiración: AccessKeyId, SecretAccessKey, SessionToken, Expiration.
  • El SessionToken es la marca de "temporal"; una credencial permanente no lo tiene.
  • ¿IdP SAML? → AssumeRoleWithSAML. ¿Web/OIDC? → AssumeRoleWithWebIdentity.
  • GetCallerIdentity no emite credenciales. CreateUser+CreateAccessKey = permanentes (lo que se quiere evitar).
  • El broker necesita credenciales AWS propias para poder llamar a STS.
