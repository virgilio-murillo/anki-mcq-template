CORS en Amazon S3 a fondo: Same-Origin Policy, preflight y reglas de bucket

Guía visual para el examen AWS Certified Developer – Associate (DVA-C02). Explica qué es CORS, por qué existe, cómo lo evalúa S3, cómo se configura, y los errores típicos que caen en el examen.

Idea en una frase: CORS es un mecanismo del navegador por el que un servidor (aquí un bucket S3) declara qué orígenes web pueden leer sus respuestas desde JavaScript. Si el bucket no lo declara, el navegador bloquea que el JavaScript lea la respuesta.

1. El problema: la Same-Origin Policy (SOP)

Los navegadores aplican una regla de seguridad llamada Same-Origin Policy: el JavaScript de una página solo puede leer respuestas de recursos que estén en el mismo origen que la página. Esto evita que un sitio malicioso lea datos de otro sitio donde tú estás autenticado.

Un origen se define por la terna esquema://host:puerto. Si cualquiera de los tres difiere, es un origen distinto (una petición cross-origin).

Página que corre el JSRecurso al que llama¿Mismo origen?Motivo
https://app.example.comhttps://app.example.com/dataSíIgual esquema, host y puerto.
https://app.example.comhttps://cdn.example.comNoHost distinto (app vs cdn).
https://app.example.comhttp://app.example.comNoEsquema distinto (https vs http).
https://app.example.comhttps://app.example.com:8443NoPuerto distinto.
https://app.example.comhttps://mi-bucket.s3.us-east-1.amazonaws.comNoHost distinto → hace falta CORS en el bucket.
ClaveCORS relaja la Same-Origin Policy de forma controlada. Es el servidor (S3) quien, con sus cabeceras de respuesta, le dice al navegador "sí, este origen puede leerme".

¿Quién hace cumplir CORS?

El navegador, no S3. S3 solo añade cabeceras Access-Control-Allow-* a su respuesta según tu configuración. El navegador decide si deja que el JavaScript lea esa respuesta. Por eso, herramientas como curl o los SDK del lado servidor no se ven afectados por CORS: no hay navegador que lo imponga.

2. Escenario típico con S3

Tienes un sitio web (SPA en React/JS) servido desde un origen, y ese JavaScript hace fetch/XMLHttpRequest directamente contra el endpoint de la API de un bucket S3 (por ejemplo para subir con PUT o leer con GET). Como el host del bucket difiere del host de la página, es cross-origin y el navegador exige CORS.

Sin las cabeceras CORS correctas en la respuesta de S3, el navegador bloquea que el JS lea el resultado.

Casos de examen frecuentesWeb font alojada en S3, sitio estático en S3 que llama a la API del propio bucket, subida directa desde el navegador a S3 con URL prefirmada. Si aparece "el navegador bloquea", "cross-origin", "CORS error en consola" → la respuesta casi siempre es configurar CORS en el bucket.

3. Peticiones simples vs. preflight (OPTIONS)

Hay dos caminos según el tipo de petición:

3.1 Petición "simple"

Si es un GET/HEAD/POST sencillo con cabeceras estándar, el navegador manda la petición directa e incluye la cabecera Origin. S3 responde y añade Access-Control-Allow-Origin. El navegador compara: si coincide, deja leer; si no, bloquea.

sequenceDiagram participant JS as JavaScript (navegador) participant S3 as Amazon S3 JS->>S3: GET /objeto (Origin: https://app.example.com) S3-->>JS: 200 OK (Access-Control-Allow-Origin: https://app.example.com) Note over JS: El navegador ve que el origen coincide -> permite leer la respuesta

3.2 Petición con preflight

Para peticiones "no simples" (por ejemplo PUT, DELETE, o con cabeceras personalizadas como Authorization o x-amz-*), el navegador envía primero una petición preflight con el método OPTIONS para preguntar permiso antes de mandar la petición real.

sequenceDiagram participant JS as JavaScript (navegador) participant S3 as Amazon S3 JS->>S3: OPTIONS /objeto (preflight)
Origin + Access-Control-Request-Method: PUT
Access-Control-Request-Headers: x-amz-... S3-->>JS: 200 OK
Access-Control-Allow-Origin / -Methods / -Headers
Access-Control-Max-Age: 3000 Note over JS: Preflight OK. El navegador cachea el permiso (MaxAgeSeconds) JS->>S3: PUT /objeto (peticion real) + Origin S3-->>JS: 200 OK + Access-Control-Allow-Origin
Truco de examenEl preflight usa el método OPTIONS. MaxAgeSeconds es cuántos segundos el navegador cachea ese permiso para no repetir el OPTIONS en cada llamada.

4. Cómo evalúa S3 la configuración CORS

Cuando S3 recibe una petición preflight, recorre las reglas y usa la primera CORSRule que coincida. Para que una regla coincida, se deben cumplir las tres condiciones:

Cabecera de la petición (navegador)Debe coincidir con este elemento de la regla
OriginAllowedOrigins
Access-Control-Request-MethodAllowedMethods
Access-Control-Request-HeadersAllowedHeaders
Clave de ordenGana la primera regla que casa, no la "mejor". Ordena de más específica a más general. Puedes tener hasta 100 reglas por configuración.
CORS no es seguridad de accesoHabilitar CORS no otorga permisos. Las ACL y las bucket policies siguen aplicando. CORS solo controla si el navegador deja leer la respuesta al JS de otro origen; la autorización real la deciden IAM/policy/ACL.

5. Los 5 elementos de una regla CORS

ElementoObligatorioQué haceReglas del comodín *
AllowedMethodsSíMétodos HTTP permitidos.Valores fijos: GET, PUT, POST, DELETE, HEAD. (No hay OPTIONS aquí: S3 lo maneja solo para el preflight.)
AllowedOriginsSíOrígenes autorizados, p.ej. https://www.example.com.Como máximo un *: https://*.example.com. * solo = cualquier origen. Puedes exigir https para solo orígenes seguros.
AllowedHeadersNoCabeceras permitidas en el preflight (via Access-Control-Request-Headers).Como máximo un * por cadena. x-amz-* habilita todas las de Amazon.
ExposeHeadersNoCabeceras de la respuesta que el JS podrá leer (p.ej. desde XMLHttpRequest).Se listan explícitamente, p.ej. ETag, x-amz-request-id.
MaxAgeSecondsNoSegundos que el navegador cachea la respuesta del preflight.Valor numérico, p.ej. 3000.
Error frecuenteExposeHeaders no "permite" nada: solo expone cabeceras de respuesta para que el JS las pueda leer. Sin listar ETag ahí, un multipart upload desde el navegador no podrá leer el ETag de cada parte.

7. Ejemplos de configuración

ImportanteEn la consola de S3, la configuración CORS debe ser JSON (la consola nueva ya no acepta XML). La API REST sigue usando XML.

7.1 JSON (consola / aws s3api) — tres reglas

Regla 1 y 2: PUT/POST/DELETE desde dos orígenes concretos. Regla 3: GET desde cualquier origen.

[
    {
        "AllowedHeaders": ["*"],
        "AllowedMethods": ["PUT", "POST", "DELETE"],
        "AllowedOrigins": ["http://www.example1.com"],
        "ExposeHeaders": []
    },
    {
        "AllowedHeaders": ["*"],
        "AllowedMethods": ["PUT", "POST", "DELETE"],
        "AllowedOrigins": ["http://www.example2.com"],
        "ExposeHeaders": []
    },
    {
        "AllowedHeaders": [],
        "AllowedMethods": ["GET"],
        "AllowedOrigins": ["*"],
        "ExposeHeaders": []
    }
]

7.2 JSON con opcionales (ExposeHeaders + MaxAgeSeconds)

[
    {
        "AllowedHeaders": ["*"],
        "AllowedMethods": ["PUT", "POST", "DELETE"],
        "AllowedOrigins": ["http://www.example.com"],
        "ExposeHeaders": [
            "x-amz-server-side-encryption",
            "x-amz-request-id",
            "x-amz-id-2"
        ],
        "MaxAgeSeconds": 3000
    }
]

7.3 El mismo ejemplo en XML (API REST)

<CORSConfiguration>
 <CORSRule>
   <AllowedOrigin>http://www.example.com</AllowedOrigin>
   <AllowedMethod>PUT</AllowedMethod>
   <AllowedMethod>POST</AllowedMethod>
   <AllowedMethod>DELETE</AllowedMethod>
   <AllowedHeader>*</AllowedHeader>
   <MaxAgeSeconds>3000</MaxAgeSeconds>
   <ExposeHeader>x-amz-server-side-encryption</ExposeHeader>
   <ExposeHeader>x-amz-request-id</ExposeHeader>
   <ExposeHeader>x-amz-id-2</ExposeHeader>
 </CORSRule>
</CORSConfiguration>

8. Cómo aplicarlo (CLI y SDK)

8.1 AWS CLI

# Aplicar la configuracion CORS (archivo local cors.json)
aws s3api put-bucket-cors --bucket <MI_BUCKET> --cors-configuration file://cors.json

# Ver la configuracion actual
aws s3api get-bucket-cors --bucket <MI_BUCKET>

# Borrar toda la configuracion CORS
aws s3api delete-bucket-cors --bucket <MI_BUCKET>

10. Troubleshooting y errores comunes

SíntomaCausa probableArreglo
"No 'Access-Control-Allow-Origin' header is present" en consola del navegadorNo hay config CORS, o el Origin no casa con AllowedOriginsAñadir/ajustar la regla; verificar esquema, host y puerto exactos.
Falla solo PUT/DELETE, el GET funcionaMétodo no está en AllowedMethods de la regla que casaIncluir el método en la regla correcta.
Preflight (OPTIONS) devuelve 403Cabecera personalizada no listada en AllowedHeadersAgregar la cabecera (o * / x-amz-*).
El JS no puede leer el ETagFalta ExposeHeadersListar ETag en ExposeHeaders.
Funciona en curl pero no en el navegadorEs un problema de CORS (solo el navegador lo impone)Configurar CORS en el bucket; no es un problema de permisos IAM.
Cambié la regla pero sigue fallando un ratoEl navegador cacheó el preflight (MaxAgeSeconds)Esperar a que expire o limpiar caché del navegador al probar.

11. Resumen para el examen (DVA-C02)

Puntos que caen
  • CORS lo impone el navegador, no S3. curl/SDK servidor no se ven afectados.
  • CORS no es autorización: ACL y bucket policies siguen aplicando.
  • Origen = esquema://host:puerto; cualquier diferencia = cross-origin.
  • Preflight = método OPTIONS antes de la petición real (para PUT/DELETE/cabeceras custom).
  • S3 usa la primera CORSRule que casa (3 condiciones: Origin, Method, Headers). Hasta 100 reglas.
  • 5 elementos: AllowedMethods, AllowedOrigins, AllowedHeaders, ExposeHeaders, MaxAgeSeconds.
  • AllowedMethods solo: GET, PUT, POST, DELETE, HEAD.
  • MaxAgeSeconds = caché del preflight en el navegador.
  • ExposeHeaders = qué cabeceras de respuesta puede leer el JS (p.ej. ETag).
  • En la consola solo JSON; la API REST usa XML.
  • Wildcard *: uno por cadena en AllowedOrigins/AllowedHeaders.
