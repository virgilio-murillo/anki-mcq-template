Preprocesamiento de texto ML · flujo automático con mínimo overhead

MLA-C01 · tarjeta de estudio · por qué la opción B (Processing Job + Lambda + S3 events)

Pregunta: preprocesar texto (limpieza, tokenización, embeddings con TensorFlow/HuggingFace) desde S3 con mínimo esfuerzo de gestión, disparado al subir datos nuevos. ¿Qué trío de acciones?

Respuesta: B — un SageMaker Processing Job (preprocesa y genera embeddings) + una Lambda que lo dispara al subir datos + S3 Event Notifications con Step Functions.

1) El flujo automático que arma la opción B

La cadena es: subes datos a S3 → una S3 Event Notification detecta la subida → dispara Lambda / Step Functions → que lanza un SageMaker Processing Job que hace la limpieza, tokenización y embeddings (con TensorFlow/HuggingFace ya incluidos). Nadie enciende ni administra servidores: el evento arranca un job administrado que corre y se apaga solo. Eso es exactamente 'mínimo esfuerzo' + 'disparado al subir datos'.

2) Por qué gana B: mínimo esfuerzo de gestión

El enunciado pide explícitamente 'mínimo esfuerzo de gestión'. B usa solo servicios administrados y serverless (Processing Job + Lambda + S3 events), así que casi no hay nada que operar. Las otras tres (A, C, D) te obligan a administrar tus propios clusters de contenedores o colas de batch (ECS/EKS/Batch), lo que es mucho más overhead: justo lo contrario de lo pedido.

3) Qué hace cada servicio (para no confundirlos)

El truco es saber para qué sirve cada pieza. SageMaker Processing Job = preprocesamiento de ML administrado (la clave). Lambda + S3 events + Step Functions = disparo y orquestación sin servidores. Glue = ETL de datos (esquemas, tablas), no embeddings de ML, y añade overhead. ECS/EKS = traer tu propia infra de contenedores. Batch = orquestar colas por lotes (capa extra innecesaria). Solo las primeras tres encajan → opción B.

4) Cómo reconocer estas preguntas

Palabras clave: 'preprocesamiento de ML administrado' → Processing Job; 'disparado al subir datos' → S3 Event Notifications + Lambda; 'orquestar sin servidores' → Step Functions; 'ETL, esquemas, tablas' → Glue (no para embeddings); y sobre todo 'mínimo esfuerzo' → descarta de entrada ECS, EKS y Batch (infraestructura propia).

Regla para el examen: preprocesamiento de ML administrado = SageMaker Processing Job (soporta TF/HuggingFace).   'disparado al subir datos' = S3 Event Notifications + Lambda (event-driven, serverless).   Glue = ETL de datos (no embeddings ML).   'Mínimo esfuerzo' descarta ECS/EKS/Batch (infra propia que administras).
