A financial services organization has built a custom machine learning (ML) model designed for real-time fraud detection. Which of the following will meet the given requirements with the least operational overhead?

Deploy the custom fraud detection model in Amazon SageMaker Neo to optimize the model, then host the optimized model on a SageMaker real‑time endpoint.
Create a model configuration within Amazon SageMaker AI, then deploy the custom fraud detection model on a serverless SageMaker endpoint.
Create a model configuration within Amazon SageMaker AI, then deploy the custom fraud detection model on an asynchronous SageMaker endpoint.
Deploy the fraud detection model on a highly available Amazon EC2 instance in an auto-scaling group. Configure an application load balancer to route the incoming requests to the EC2 instance.
Incorrect
Amazon SageMaker AI is a fully managed machine learning (ML) service that enables data scientists and developers to efficiently build, train, and deploy ML models in a production-ready environment. It offers a user interface for executing ML workflows, making its tools accessible across various integrated development environments (IDEs).

With SageMaker AI, you can store and share your data without the need to set up and manage your own servers. This allows you and your organization to focus on collaboratively building and developing your ML workflows more quickly. SageMaker AI provides managed ML algorithms that can efficiently process vast amounts of data in a distributed setting. Additionally, it supports the use of your own algorithms and frameworks, offering flexible distributed training options tailored to your specific needs. You can easily deploy a model into a secure and scalable environment directly from the SageMaker AI console in just a few steps.

Amazon SageMaker Serverless Inference is a dedicated option for deploying and scaling machine learning models without the need to configure or manage underlying infrastructure. It is particularly suitable for workloads with intermittent traffic patterns that can accommodate cold starts.

With on-demand Serverless Inference, compute resources are automatically launched and scaled based on traffic, so there’s no need to select instance types or manage scaling policies. This simplifies the process by eliminating the challenges associated with server management.

Serverless Inference works seamlessly with AWS Lambda, offering high availability, built-in fault tolerance, and automatic scaling. Its pay-per-use model makes it a cost-effective choice for workloads with infrequent or unpredictable traffic. During periods with no requests, Serverless Inference can scale your endpoint down to zero, helping you reduce costs.

serverless SageMaker endpoint

Your serverless endpoint must have a minimum RAM size of 1024 MB (1 GB), with a maximum RAM size of 6144 MB (6 GB). The available memory sizes you can select are 1024 MB, 2048 MB, 3072 MB, 4096 MB, 5120 MB, and 6144 MB. Serverless Inference automatically assigns compute resources based on the memory size you choose. By selecting a larger memory size, your container will have access to more vCPUs. It’s advisable to set the memory size to be at least as large as your model size.

You can configure a maximum concurrency of up to 200 for a single endpoint. Additionally, you can host a total of 50 serverless endpoints in a single region. The maximum concurrency limit for an individual endpoint ensures that it does not consume all the invocations allowed for your account. Any invocations that exceed this limit will be throttled.

Hence, the correct answer is: Create a model configuration within Amazon SageMaker AI, then deploy the custom fraud detection model on a serverless SageMaker endpoint. It provides real-time inference with minimal infrastructure management. SageMaker serverless endpoints automatically scale based on traffic, support models up to 6 GB, and eliminate the need to manage instances, perfect for a fraud detection model under 5 GB handling up to 50 concurrent requests.

The option that says: Deploy the custom fraud detection model in Amazon SageMaker Neo to optimize the model, then host the optimized model on a SageMaker real-time endpoint is incorrect because while SageMaker Neo can typically optimize model performance, deploying to a real-time endpoint still requires provisioning and managing compute instances. This introduces more operational overhead than a serverless endpoint, which contradicts the requirement to minimize infrastructure management.

The option that says: Create a model configuration within Amazon SageMaker AI, then deploy the custom fraud detection model on an asynchronous SageMaker endpoint is incorrect because asynchronous endpoints are primarily designed for batch or long-running inference tasks, not real-time use cases. Fraud detection requires immediate responses, so this option would introduce unacceptable latency.

The option that says: Deploy the fraud detection model on a highly available Amazon EC2 instance in an auto-scaling group. Configure an application load balancer to route the incoming requests to the EC2 instance is incorrect because it involves significant infrastructure management, provisioning, scaling, patching, and configuring load balancing. This goes against the goal of minimizing operational overhead.

CreateEndpointConfig creates an endpoint configuration that SageMaker hosting services uses to deploy models. In the configuration, you identify one or more models, created using the CreateModel API, to deploy and the resources that you want SageMaker to provision. Then you call the CreateEndpoint API.

In the request, you define a ProductionVariant , for each model that you want to deploy. Each ProductionVariant parameter also describes the resources that you want SageMaker to provision. This includes the number and type of ML compute instances to deploy.

If you are hosting multiple models, you also assign a VariantWeight to specify how much traffic you want to allocate to each model. For example, suppose that you want to host two models, A and B, and you assign traffic weight 2 for model A and 1 for model B. SageMaker distributes two-thirds of the traffic to Model A, and one-third to model B.

ProductionVariant identifies a model that you want to host and the resources chosen to deploy for hosting it. If you are deploying multiple models, tell SageMaker how to distribute traffic among the models by specifying variant weights.

ProductionVariant and InitialVariantWeight

InitialVariantWeight determines initial traffic distribution among all of the models that you specify in the endpoint configuration. The traffic to a production variant is determined by the ratio of the VariantWeight  to the sum of all VariantWeight values across all ProductionVariants.

Amazon Bedrock

A knowledge base in Amazon Bedrock serves as a managed data retrieval layer for RAG workflows. When a knowledge base is created, it can be connected directly to an Amazon S3 bucket or other data repositories containing unstructured or semi-structured content such as PDFs, manuals, FAQs, or reports. Bedrock automatically performs data ingestion, document parsing, text chunking, and embedding generation using an integrated vector store. The service manages the synchronization of the data source and ensures that newly uploaded or modified documents in S3 are continually available for retrieval. When a user submits a query through the Amazon Bedrock API, the service retrieves the most semantically relevant document fragments from the knowledge base and injects them into the LLM’s prompt context. This process enables the model to generate responses grounded in verified internal data, improving factual accuracy and reducing hallucinations. By leveraging RAG, the model can dynamically access the latest information without undergoing additional fine-tuning or retraining cycles.

This architecture combines the flexibility of Amazon S3 as a scalable data storage service with the intelligence and automation of Amazon Bedrock. It allows teams to build chatbots and other generative AI solutions that understand proprietary documents, maintain data freshness, and scale seamlessly across enterprise workloads. Additionally, Bedrock integrates securely with AWS Identity and Access Management (IAM), ensuring that data access and inference requests are fully auditable and compliant with enterprise security standards.

In summary, creating a knowledge base in Amazon Bedrock, connecting it to an Amazon S3 bucket, and invoking RAG queries through the Bedrock API provides a powerful and fully managed solution for grounding an LLM’s responses with enterprise data. This workflow aligns with AWS best practices for implementing generative AI systems that require contextual accuracy, operational efficiency, and continuous adaptability.

Hence, the correct answer is: Configure a knowledge base in Bedrock. Add the S3 bucket as the connected data source, and utilize the Bedrock API to perform RAG queries that dynamically combine document retrieval with LLM generation.

While Amazon Kendra can index and semantically search the S3 documents, it is only a retrieval service. It does not natively perform retrieval-augmented generation (RAG) integration with a large language model. Building a custom connection between Kendra and an LLM would require manual orchestration, data formatting, and prompt engineering. This approach would simply increase operational complexity and reduce the benefits of a fully managed, scalable solution like Amazon Bedrock Knowledge Bases.

Fine-tuning is typically used to adjust a model’s tone, structure, or task-specific behavior, not to embed continuously changing enterprise knowledge. Fine-tuning permanently modifies model parameters and would require repeated retraining whenever new policies or regulations are added. This method would be costly, time-consuming, and not suitable for regulatory data that must remain up-to-date. Developers would have to handle embedding generation, vector storage, and nearest-neighbor search logic independently. This solution would simply replicate capabilities already offered natively through Bedrock Knowledge Bases, which automate the ingestion, embedding, retrieval, and integration of proprietary content into model responses.
