Incorrect
Amazon Transcribe streaming processes live audio as it arrives and returns transcription events incrementally. During an active speech segment, Amazon Transcribe produces partial results before the segment is finalized, allowing an application to act on interim text instead of waiting for the customer to pause or finish speaking. For latency-sensitive applications, partial-result stabilization can further limit how much of the latest transcription may change, trading some accuracy for faster stabilized output. This makes Amazon Transcribe suitable for real-time contact center workflows where reducing speech-to-text delay is important.

Amazon Transcribe streaming

Amazon Bedrock’s InvokeModelWithResponseStream API runs model inference and returns the generated output as a stream of response chunks rather than waiting until the entire response has been generated. By sending incoming transcript fragments to a streaming-capable foundation model, the application can begin receiving model output earlier. Amazon API Gateway WebSocket APIs provide persistent two-way communication between connected clients and backend services, allowing the backend to push each generated response update to the agent interface as it becomes available. Together, these services reduce end-to-end latency by avoiding unnecessary waits at the transcription, generation, and delivery stages.

This architecture therefore maintains a continuous path from live audio to partial transcription, streamed model inference, and real-time delivery to the agent application. The design relies on managed AWS services and avoids buffering complete transcription segments or model responses before processing the next stage.

Hence, the correct answer is: Enable partial-result streaming in Amazon Transcribe so interim speech-to-text segments are available while the customer is still talking. Send the transcript fragments to Amazon Bedrock with the InvokeModelWithResponseStream API, then deliver the streamed model output to contact center agents through an Amazon API Gateway WebSocket API.

The option that says: Stream the customer audio to Amazon Transcribe, but wait for each transcription segment to be finalized before sending the text to Amazon Bedrock with the InvokeModel API. Return the completed model response to the agent application through an Amazon API Gateway REST API is incorrect because it typically introduces delay at multiple stages. Waiting for finalized transcription segments prevents the application from processing interim speech, while InvokeModel returns a completed response instead of streaming generated output. A REST request-response pattern also does not provide the persistent two-way connection required for continuously pushing incremental updates to agents.

The option that says: Send the live audio to Amazon Transcribe with partial results enabled and write each transcript fragment to Amazon Kinesis Data Streams. Use AWS Lambda to batch the fragments, invoke Amazon Bedrock after enough context has accumulated, and return the generated response through an Amazon API Gateway WebSocket API is incorrect because batching transcript fragments would primarily delay when model inference begins. Although Kinesis and Lambda can process streaming workloads, deliberately accumulating multiple fragments before invoking Amazon Bedrock conflicts with the requirement to minimize the time from speech input to the first generated suggestion.

The option that says: Use Amazon Transcribe streaming with partial results enabled and send each transcript fragment to Amazon Bedrock by using the InvokeModelWithResponseStream API. Buffer all generated response chunks in AWS Lambda and send the completed response to agents through an Amazon API Gateway WebSocket API is incorrect because buffering the model output would simply remove the latency advantage of response streaming. InvokeModelWithResponseStream is designed to expose generated chunks as they become available, and API Gateway WebSocket APIs allow backend services to send messages to connected clients without waiting for the complete model response.
